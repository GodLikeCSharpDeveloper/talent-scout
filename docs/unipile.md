# Подключение Unipile

## Разделение ответственности

```text
Features/*/Handlers
    → ILinkedInGateway / ILinkedInProfiles / ILinkedInContacts / ILinkedInConversations
    → Providers/Unipile/Adapters
    → Providers/Unipile/Api (IUnipileSearchApi и остальные контракты)
    → Providers/Unipile/Http/IUnipileHttpClient
    → HttpClient
```

`Http` отправляет HTTP, сериализует запросы и читает ответы. `Api` содержит адреса и форматы конкретных методов Unipile; метод поиска получает одну страницу без обхода результатов и загрузки профилей. `Adapters` переводят DTO провайдера в контракты приложения. У `ILinkedInGateway` только операции поиска и отправки, без публичных свойств настройки аккаунта. Профили, контакты, диалоги и администрирование выделены отдельными интерфейсами.

Добор до нужного числа новых участников, пропуск существующих, загрузка полного профиля и сохранение находятся в `SearchCandidatesHandler`. `SearchCandidatePageHandler` разрешает локацию, обрабатывает прикладной курсор и остаток страницы. Для кандидатов, которые уже есть в общей базе, полный профиль повторно не загружается. Пагинация списка аккаунтов и регистрация нужных webhook также выполняются хендлерами фичи.

Настройки интеграции берутся через `IOptions<LinkedInOptions>`. Хендлеры работают с нашими интерфейсами, а формат webhook Unipile разбирается на отдельной входной границе. Репозитории и SQL остаются в `TalentScout.Data`.

Реализация использует REST API **v1** Unipile. Схемы v2 с событиями `message.new` сюда передавать нельзя. Сейчас выбран LinkedIn Classic; поиск через Sales Navigator и Recruiter этим адаптером не выполняется.

## Настройки

Подключить аккаунт LinkedIn в Unipile Dashboard, взять DSN, API key и Account ID. В `.env` заполнить:

```dotenv
LINKEDIN_BASE_URL=https://api1.unipile.com:13111
LINKEDIN_API_KEY=<ключ Unipile>
LINKEDIN_ACCOUNT_ID=<ID подключённого LinkedIn аккаунта>
LINKEDIN_WEBHOOK_SECRET=<отдельный случайный секрет минимум 32 символа>
LINKEDIN_WEBHOOK_URL=https://your-domain.example/api/webhooks/unipile
LINKEDIN_USE_INMAIL=false
PIPELINE_WORKER_ENABLED=false
```

DSN выше приведён как пример: использовать адрес своего приложения Unipile **без** `/api/v1`. Compose передаёт значения в секцию `LinkedIn` appsettings. Provider установлен в `Unipile`; пустой API key оставляет интеграцию отключённой. Секреты не передаются в UI. В текущем MVP один аккаунт рекрутера выбирается конфигом для всего приложения.

Webhook URL должен быть публичным HTTPS-адресом. Публикация через HTTPS/reverse proxy настраивается в окружении; Compose по-прежнему публикует API на loopback. Внешний сервис и реальные аккаунты при добавлении кода не подключались.

`LINKEDIN_USE_INMAIL=false`: первое сообщение отправляется доступному контакту. Иначе нужно явно вызвать команду запроса на добавление и дождаться принятия. `true` включает InMail для нового диалога; доступность функции и кредиты определяет подключённый LinkedIn аккаунт.

При запуске настроенного бэка `LinkedInWebhookStartupService` автоматически регистрирует подписки на сообщения и принятие контакта. Он выполняется до запуска воркеров. Повторный запуск использует существующие подписки по имени и URL и создаёт недостающие. Если Unipile не настроен, шаг пропускается. Если ключ задан, но callback URL неверен или регистрация не удалась, запуск прерывается: воркеры не начинают рассылку без подписок.

Для фоновой обработки основной воронки включить `PIPELINE_WORKER_ENABLED=true` после настройки Unipile и ключа OpenAI. Отдельный worker входящих webhook работает при настроенном Unipile даже при выключенной автоматической воронке: он сохраняет ответы, но сам не вызывает AI и не отправляет сообщения.

## Маршруты

Управляющие маршруты требуют обычный `X-Api-Key` TalentScout API.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| GET | `/api/integrations/linkedin` | Состояние конфигурации без секретов |
| GET | `/api/integrations/linkedin/accounts` | Подключённые LinkedIn аккаунты Unipile |
| POST | `/api/integrations/linkedin/profiles/import` | Получить профиль по `identifier` и сохранить кандидата |
| GET | `/api/integrations/linkedin/webhook-events` | Сохранённые события, попытки и причины ожидания; `page`/`pageSize` |
| GET | `/api/enrollments/{id}/linkedin/contact-status` | Актуальная возможность написать, наличие связи и ожидающего запроса |
| POST | `/api/enrollments/{id}/linkedin/connection-request` | Явно отправить запрос на добавление для одобренного кандидата |
| GET | `/api/enrollments/{id}/linkedin/conversation` | Привязка диалога, состояние запроса и `conversationUrl` |
| PUT | `/api/enrollments/{id}/linkedin/conversation` | Явно привязать/восстановить диалог по `chatId` |
| POST | `/api/webhooks/unipile` | Приём событий с отдельным `X-Unipile-Secret` |

Поиск использует прежний `POST /api/campaigns/{id}/search`. Отправка — прежние команды `send-introduction` и `send-interview-invitation`; отдельной обходной отправки без подтверждений нет.

Примеры тел запросов:

```json
{ "identifier": "linkedin-public-identifier-or-provider-id" }
```

```json
{ "note": "Здравствуйте, хочу обсудить вакансию." }
```

```json
{ "chatId": "unipile-chat-id" }
```

## Поиск и профили

Поиск Classic передаёт ключевые слова кампании; текст локации сначала переводится в ID параметра LinkedIn. Если локация не найдена, API возвращает 400. Из результатов дополнительно загружается профиль с опытом работы для оценки AI. Недоступные поля профиля остаются пустыми: опыт и навыки не придумываются.

Пагинация провайдера скрыта за подписанным курсором TalentScout, привязанным к аккаунту, запросу и локации. Если провайдер вернул больше профилей, чем нужно для текущего добора, оставшиеся ID сохраняются в курсоре. Он действует 30 минут; после потери ключей Data Protection, например при пересоздании контейнера без сохранения ключей, поиск следует начать заново. Повторный поиск пропускает уже участвующих кандидатов по существующей логике.

## Ответы и принятие запроса

Сервис старта создаёт две подписки v1: `message_received` и `new_relation`, ограниченные выбранным Account ID. Обе передают `X-Unipile-Secret`. Ручного маршрута регистрации в HTTP API нет. При смене секрета обновить header у существующих webhook в Unipile Dashboard либо удалить старые регистрации: при следующем старте бэк создаст недостающие.

Входящий endpoint проверяет отдельный секрет, аккаунт, направление сообщения и структуру payload. Исходящие сообщения, группы и служебные события игнорируются. Валидное событие сначала сохраняется в `LinkedInWebhookEvents`; только после этого возвращается 200. Уникальный ключ аккаунт + внешний ID защищает от повторной доставки. Ошибка сохранения не подтверждается успешным ответом.

Worker входящих событий берёт записи с временной блокировкой, находит сохранённую связь с участием кандидата и переносит текст в обычную историю сообщений. События без привязки или с неподтверждённой первой отправкой остаются в очереди с причиной и повторной попыткой. Вложения направляются в `NeedsReview`: AI не делает выводов по их содержимому. Далее основной worker анализирует текстовый ответ и соблюдает обе настройки подтверждения кампании.

`new_relation` подтверждает принятие запроса и возвращает кандидата в очередь основного worker. У Unipile это событие может запаздывать до 8 часов; при необходимости пользователь может явно обновить `/contact-status`. Ожидающий кандидат не вызывает проверку профиля каждые 30 секунд: назначается отложенная попытка. Запрос на добавление сам по себе ещё не является первым сообщением воронки.

## Диалоги и неопределённые отправки

Перед отправкой резервируется связь аккаунт + получатель → участие в кампании. Один диалог не назначается двум кампаниям автоматически. Если он уже принадлежит другому участию, возвращается 409; неоднозначный ответ не направляется наугад в одну из кампаний.

После первой отправки сохраняется `chatId`, последующие сообщения отправляются в тот же чат. Родной ID LinkedIn получается из webhook или деталей чата; из него формируется `conversationUrl`. Внутренний ID Unipile не подставляется в URL LinkedIn. Явная привязка чата проверяет аккаунт и получателя у провайдера. Открывать URL нужно под LinkedIn аккаунтом с доступом к переписке.

У API v1 Unipile не предполагается гарантия идемпотентности по нашему ключу. HTTP-повторы отправки выключены. После неоднозначного результата сообщение или запрос на добавление остаётся `Unknown`/`Sending` и автоматически не повторяется. Для сообщений используется существующая команда сверки доставки; внешние ID сообщений имеют вид `unipile:{accountId}:{messageId}`. При необходимости восстановить привязку чата через `PUT .../linkedin/conversation` после проверки провайдера. Принятый запрос на добавление также может быть подтверждён событием `new_relation`.

Сущности, контекст и репозитории находятся в `TalentScout.Data`; контроллеры работают через хендлеры. Миграция `AddUnipileConversationsAndInbox` добавляет таблицы диалогов и входящих событий.

Автоматическая регистрация проверяется тестами жизненного цикла хоста, удалённого маршрута и HTTP-запросов к локальному серверу провайдера. Эти тесты не требуют Docker. PostgreSQL/Testcontainers, применение миграций и реальное подключение к Unipile отдельной проверки требуют; сохранённый OpenAPI после интеграции пока не обновлён.
